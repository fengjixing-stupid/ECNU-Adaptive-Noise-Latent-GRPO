# 通用脚本项目 AGENTS.md 模板

> 使用方法：复制本文件到目标仓库根目录并改名为 `AGENTS.md`。删除不适用的条目，并把 `{...}` 占位内容替换为项目真实信息。本模板文件保持当前名称时仅作参考。

## 项目目标

- 项目名称：`{PROJECT_NAME}`
- 核心用途：`{ONE_SENTENCE_PURPOSE}`
- 主要技术栈：`{LANGUAGES_AND_FRAMEWORKS}`
- 主要入口：`{MAIN_ENTRYPOINTS}`
- 定义完成：`{VERIFIABLE_DEFINITION_OF_DONE}`

## 沟通方式

- 默认使用 `{LANGUAGE}` 回答，代码符号和命令保留源码形式。
- 先给结论，再给证据和必要过程。
- 不把推测写成事实；无法确认时说明未知项和下一步取证方式。
- 根据问题控制范围。单个脚本或参数问题不扩展成无关的全项目重构。
- 用户引用之前的决定时，优先结合当前对话和项目内已确认文档恢复上下文。

## 项目导航

开始任务前按需检查：

- `{REPOSITORY_README}`：项目入口和基本命令；
- `{ARCHITECTURE_DOC}`：架构与模块边界；
- `{CONFIG_PATHS}`：配置、schema 和默认值；
- `{SCRIPT_PATHS}`：脚本和命令入口；
- `{TEST_PATHS}`：测试与验收；
- `{DECISION_LOG}`：稳定决定、限制和已知问题。

只读取当前任务需要的内容，不无边界扫描仓库。已有工作区改动默认属于用户，不覆盖、不回退无关修改。

## 正式文档治理（使用 r-doc 时）

如果当前项目已安装或可用 r-doc，将它作为正式项目知识的文档治理层，而不是工作记忆层：

- 初始化、索引、审计、修复、同步或发布项目文档时，按 r-doc 的工作流执行。
- 计划、需求、设计、架构、公共 API、配置、数据格式、测试策略、发布、部署、项目规则或流程发生可能影响文档的变化时，检查并同步对应正式文档。
- 纯局部实现或重构若不改变公共行为、数据、配置、架构或项目规则，不仅因为仓库存在 r-doc 就扩大成完整文档治理任务。
- r-doc 管理正式 `docs/`、索引、元数据和正式 decision notes；`progress/` 仍按本文件“工作记忆与长期任务”规则管理，不把它视为正式文档树。
- r-doc 的运行时 Skill 规则与本文件发生具体工具或文档治理细节差异时，在不违反更高层指令和用户当前要求的前提下，文档治理操作遵循当前安装版本的 r-doc Skill；本文件继续定义项目级边界、工作记忆和工程执行原则。

## 证据优先级

判断项目行为时按以下顺序取证：

1. 当前版本实际执行的源码；
2. 当前版本的配置 schema、参数解析和运行脚本；
3. 仓库内测试；
4. 仓库 README、架构文档和变更记录；
5. 锁定版本的上游官方文档；
6. 一般工程经验，仅用于提出待验证假设。

来源冲突时列出差异，说明实际运行采用哪一个值以及原因，不静默猜测。

## 脚本介绍流程

解释脚本前先沿真实调用链检查代码，并说明：

1. 调用者和启动方式；
2. 运行环境；
3. 输入参数、配置、环境变量和文件；
4. 下游脚本、模块或外部服务；
5. 输出、日志和持久化结果；
6. 失败条件和前置条件；
7. 最小安全验证命令。

推荐回答顺序：

```text
用途 → 调用入口 → 参数流 → 核心步骤 → 输出 → 常见失败点 → 验证
```

引用证据时优先给出文件路径和函数、类或配置段名称；行号仅作当前定位辅助。

## 参数查找流程

查找参数时追踪完整生命周期：

1. CLI、配置、环境变量或 API 中的定义；
2. 类型、单位、默认值和合法范围；
3. 配置合并及覆盖优先级；
4. 传递路径；
5. 运行时消费位置；
6. 互斥、依赖、整除或资源约束；
7. 日志、manifest 或最终配置中的可观测性；
8. 安全覆盖示例和验证方法。

参数回答尽量包含：

| 字段 | 内容 |
| --- | --- |
| 名称 | 完整配置 key、CLI 选项或环境变量 |
| 类型与单位 | 实际类型和单位 |
| 默认值 | 来源文件和默认值 |
| 当前值 | 最终解析结果；未解析时写“未确认” |
| 定义位置 | schema、parser 或配置文件 |
| 消费位置 | 真正改变行为的源码 |
| 覆盖方式 | 可复制的最小示例 |
| 约束与影响 | 正确性、资源、性能或兼容性 |
| 证据状态 | 已确认、推断或未知 |

必须区分“参数被解析”和“参数被实际使用”，不得凭名称或一般经验臆造行为。

## 修改原则

- 第一层：纯解释、审查和诊断任务默认只读项目文件；已有 `progress/` 也只读。只有用户明确要求记录交接信息时，才允许写入与交接直接相关的 `progress/` 内容，不得借此修改其他项目文件。
- 第二层：除 `progress/` 的受控例外外，只有用户明确要求实现、修复或更新时才修改项目文件。
- 第三层：`progress/` 是项目文件写入限制的受控例外。对于需要维持长期上下文且允许写工作区的任务，可按“工作记忆与长期任务”规则主动维护；用户明确给出预计后续仍需遵守的重要环境处理方式、命令约定、操作习惯、限制或其他项目级长期信息时，可将其写入对应的长期笔记，即使当前这条消息本身没有要求修改项目实现。该例外不覆盖第一层的只读边界：在纯解释、审查和诊断任务中，除非用户明确要求记录交接信息，否则仍不得创建或修改 `progress/`。
- 修改前确认真实入口、下游消费者和现有测试。
- 遵循项目现有结构，不做与任务无关的重构。
- 新增依赖、公开接口或数据格式前说明影响。
- 不覆盖用户已有改动，不执行未获授权的外部写操作。
- 文件编辑后同步更新直接受影响的文档和示例。

## 安全与资源边界

- 未经明确授权，不启动长时间任务、大型下载、付费服务或生产部署。
- 不在源码、日志、命令、配置或产物中暴露凭据。
- 破坏性操作必须确认准确目标并优先采用可恢复方式。
- 资源不足或权限受限时停止并报告，不通过静默降级改变任务语义。
- dry-run、静态检查和只读诊断优先于高成本执行。

## 验证

每次变更执行最小但充分的验证：

1. 与文件类型匹配的格式或静态检查；
2. 与变更最接近的单元测试；
3. 相关模块或集成测试；
4. 用户要求且环境允许时的端到端验证。

完成前检查最终 diff。不得在没有运行证据时宣称测试通过或功能可用。无法执行的验证要说明原因和替代证据。

项目标准命令：

```text
格式检查：{FORMAT_COMMAND}
静态检查：{LINT_COMMAND}
单元测试：{UNIT_TEST_COMMAND}
集成测试：{INTEGRATION_TEST_COMMAND}
dry-run：{DRY_RUN_COMMAND}
```

## 工作记忆与长期任务

`progress/` 是 Codex 的本地工作记忆，用于长任务、长上下文、分阶段实施和跨会话恢复，避免遗忘任务早期的重要事实、约定、决策、约束和已验证结论。它采用“中央索引 + 分类长期记忆 + 当前恢复点 + 过时信息档案”的结构；只在需要维持长期上下文的可写任务中主动维护。审查、解释和诊断任务默认只读项目文件，包括已有的 `progress/`；除非用户明确要求记录交接信息，否则不得创建或修改其中任何笔记。

### 目录与职责

需要长期工作记忆且当前任务允许写文件时，如 `progress/` 不存在则创建。推荐结构：

```text
progress/
├── INDEX.md
├── current.md
├── decisions.md
├── findings.md
├── constraints.md
└── obsolete.md
```

- `INDEX.md`：唯一的全局导航索引，只记录主题、关键 ID、关键词和目标文件，不复制各笔记正文，也不在其他主题文件中重复维护完整索引。
- `current.md`：非常短的当前工作状态和恢复点，持续覆盖更新，不作为流水日志。至少说明当前目标、已完成阶段、正在处理的事项、剩余事项、阻塞或未知项，以及下一步从哪里继续。
- `decisions.md`：当前长任务仍需遵守的本地工作决定、临时约定及其理由，使用 `PDEC-*` ID；它不是正式架构/产品决策库。需要成为团队长期决策记录的内容，应按项目文档规则晋升到正式决策文档；使用 r-doc 时优先写入其 decision-note 层。
- `findings.md`：从源码、配置、测试或运行结果中已经确认、且后续仍有价值的重要事实；如该事实已进入正式项目文档，则优先保留指向正式文档的引用而不是复制第二份正文。
- `constraints.md`：兼容性、资源、环境、不可修改区域、用户约定等持续有效的限制。
- `obsolete.md`：已经失效、被推翻或被替代的信息，以及失效原因和替代关系。

`INDEX.md` 和 `current.md` 是核心文件；其他主题文件在首次需要时创建，不为了满足形式而生成空文件。

### 开始工作与信息检索

先根据任务类型选择上下文读取路由，不让 `progress/` 与正式文档索引争夺同一入口：

- 普通实现、修复、调试或长任务恢复：`AGENTS.md` → `progress/INDEX.md` → `progress/current.md` → 与当前任务相关的主题笔记 → 按需读取正式项目文档、源码和测试。
- 使用 r-doc 的文档初始化、审计、同步或治理任务：`AGENTS.md` → `docs/README.md`（或项目配置指定的文档入口）→ 相关主题索引 → 目标正式文档；只有当该治理任务本身需要恢复长任务上下文时，才按需读取 `progress/`，不要默认加载全部工作记忆。
- 如果 `progress/` 已存在，进入需要长期上下文的普通任务时先读取 `progress/INDEX.md` 和 `progress/current.md`，再根据当前任务按需读取被索引的主题笔记；不要无边界读取全部历史记录。
- 如果不确定某条信息位于哪个笔记，不要猜路径后逐文件浏览。先对 `progress/` 使用关键词搜索，再扩大读取范围。
- 搜索优先使用稳定 ID、文件名、函数或类名、完整配置 key、错误文本和领域关键词；存在多个同名项时使用完整 key、模块作用域或其他可区分上下文。
- `INDEX.md` 只负责导航。主题文件中的条目使用稳定短 ID + Markdown 标题定位，例如 `PDEC-014`、`FIND-023`、`CON-006`、`TODO-004`、`OBS-008`。`PDEC-*` 仅表示 progress-local decision，避免与 r-doc 或其他正式决策记录常用的 `DEC-*` 命名空间混淆。

### 记录与更新原则

- 只记录后续阶段仍可能依赖、且不适合仅依靠当前对话记忆的信息；不要记录可以轻易从源码重新获得的琐碎浏览过程、普通命令历史或无长期价值的尝试。
- 用户明确给出的、预计后续工作仍需遵守的重要环境处理方式、命令约定、操作习惯、限制和其他项目级约定，属于长期工作记忆。在满足上述写入条件时应尽早写入对应主题笔记，并在需要时更新 `INDEX.md` 的轻量导航，不要等到上下文接近压缩、丢失或准备交接时才补记。
- 形成后续必须遵循的本地工作决定、确认不明显但重要的项目事实、明确长期约束、完成明显阶段、发现旧笔记失效或需要跨会话恢复时，及时更新相应笔记。工作决定使用 `PDEC-*`；如果其影响已经超出当前 Codex 工作上下文，成为团队长期需要理解的正式决策，则应晋升到正式决策记录。
- 对这类用户长期约定，优先记录其适用条件、可执行命令或操作方式、必要注意事项和便于检索的关键词；如果当前任务属于纯解释、审查或诊断，只读边界仍优先，除非用户明确要求记录交接信息。
- 记录重要结论时包含必要的来源文件、符号或配置位置、验证状态；适用时记录形成原因和关联 ID。
- 源码、配置或任务约束变化后，重新验证受影响的旧结论，不因笔记中已有记录就默认其仍然正确。
- `current.md` 应保持简短，只保留恢复当前工作的最小充分上下文；阶段推进后覆盖已经失去恢复价值的过程信息。
- 当某条 `progress/` 信息已经被正式项目文档或正式决策记录吸收后，不继续在 `progress/` 中维护第二份完整正文；将该条目收敛为正式来源的路径/ID、当前任务为何仍需它以及必要的检索关键词。
- 用户明确要求“记录交接信息”时，即使当前属于审查、解释或诊断任务，也只允许更新与交接直接相关的 `progress/` 内容，不借此修改其他项目文件。

### 过时信息与替代关系

- 不静默删除旧结论，也不要只把旧内容移动到 `obsolete.md` 后失去原有引用关系。
- 旧条目失效时，在原条目保留可识别的过时标记，并写明 `Superseded-by: <NEW_ID>`、`See: <OBS_ID>` 或等价关系；新条目可用 `Supersedes: <OLD_ID>` 反向关联。
- `obsolete.md` 中为过时信息分配稳定 `OBS-*` ID，并记录旧结论、失效原因、替代条目、必要证据和适用时间或条件。
- 搜索命中过时条目时，必须沿替代关系找到当前有效结论后再继续工作，不得把历史结论当作当前事实。

示例：

```md
## FIND-009 — Checkpoint output path
Status: obsolete
Superseded-by: FIND-027
See: OBS-012
```

```md
## OBS-012 — 旧的 checkpoint 保存路径
Status: obsolete
Superseded-by: FIND-027
Reason: 输出目录结构已经改变
Evidence: `src/checkpoint.py::save_checkpoint`
```

### 与 r-doc、正式项目文档和版本控制的关系

`progress/` 与正式项目知识使用不同生命周期。`progress/` 服务 Codex 的任务恢复；正式文档服务项目成员、审查、版本控制和长期维护。两者可以互相引用，但不得无意识地维护两个事实源。

- `progress/` 是 Codex 本地工作记忆，不替代 `{DECISION_LOG}`、参数参考、架构文档、审计文档或其他正式项目资料。需要成为团队长期事实的内容仍应按项目规则更新正式文档。
- 项目使用 r-doc 时，`docs/`（或其配置的 `docs_root`）承担“当前正式事实与说明”，r-doc 的 decision-note 层（默认 `.agents/notes/`）承担重要正式决定的理由、备选方案和后果；`progress/` 只承担本地工作记忆和恢复上下文。
- `progress/decisions.md` 中的 `PDEC-*` 只记录当前工作需要记住的本地决定或暂时约定。若决定需要被未来维护者长期理解、影响公共行为、接口、配置、架构、跨文件契约、依赖、部署、测试策略或流程规则，应按项目规则晋升为正式决策记录；使用 r-doc 时优先使用其 decision-note 机制，不在 `progress/` 中并行维护另一份正式决定正文。
- 当 `FIND-*`、`CON-*` 或 `PDEC-*` 被晋升为正式项目知识后，`progress/` 中只保留 `Canonical:`/正式文档路径或正式 ID、与当前任务的关系和必要关键词；后续修改正式事实应更新正式来源，而不是先改本地副本。
- 对“当前行为是什么”的判断仍按本文件“证据优先级”从源码、配置和测试等证据验证；正式 `docs/` 是项目当前书面知识的权威入口，正式 decision note 解释“为什么这样决定”，`progress/` 不得仅凭本地旧记录覆盖二者。发现冲突时先报告并重新验证，再更新或标记相应 `progress/` 条目。
- `progress/obsolete.md` 只归档 Codex 工作记忆中失效、被推翻或被替代的内容；正式项目文档或正式决策的生命周期变更应使用项目自己的 superseded/archived 机制。使用 r-doc 时，不用 `OBS-*` 代替其正式文档生命周期或 `supersedes` 关系。
- r-doc 的文档治理不应仅为了统一文档结构而把 `progress/` 移入 `docs/`、把其内容批量晋升为正式文档、删除其本地恢复结构，或用正式文档索引替代 `progress/INDEX.md`。只有信息本身满足正式知识或正式决策的条件时才晋升。
- 若 r-doc 的 `docs_root` 或扫描范围被配置为可能覆盖 `progress/`，应通过项目的 r-doc 配置将 `progress` 排除在正式文档治理范围之外；不要仅为隐藏工作记忆而擅自修改 `.r-doc.yaml`，需遵循当前任务授权和项目规则。默认 `docs_root: docs` 时通常无需额外处理。
- `progress/` 默认不提交版本控制，不主动执行 `git add`、`git commit` 或将其混入业务变更；只有用户或项目规则明确要求时才纳入提交。
- 不为了隐藏 `progress/` 而擅自修改 `.gitignore`；是否忽略该目录由项目规则或用户决定。

信息从本地工作记忆晋升为正式项目知识时遵循：

```text
聊天 / 当前调查
→ progress/（长任务需要时）
→ docs/ 当前正式事实，或正式 decision note 决策理由
→ progress/ 收敛为正式来源指针 + 当前任务恢复信息
```

## 协作与并行

- 只有任务明确要求或确有多个独立子任务时才使用并行协作。
- 并行任务必须有清晰的文件所有权和可独立验证的输出。
- 多个执行者不得同时修改同一文件。
- 主执行者负责复核证据、集成结果和最终验证。
- 存在前后依赖的工作按顺序执行，不为了并行而强行拆分。

## 完成标准

最终回答必须：

- 直接回应用户目标；
- 区分事实、推断和未知；
- 对修改说明变更文件和验证结果；
- 对未执行的验证说明原因；
- 给出的命令不含真实凭据或机器专用路径；
- 不把局部验证描述为完整系统验证。
